## v0.5.2 — Жёсткое разграничение прав (RBAC)

Введена единая серверная матрица доступа для ролей **Заявитель / Техник / Диспетчер / Руководитель / Администратор**. Ограничения проверяются не только интерфейсом, но и в web-маршрутах и REST API.

- заявитель видит только собственные заявки;
- техник видит только назначенные ему заявки, только он может вести свой таймер и менять рабочие статусы по разрешённой цепочке;
- диспетчер назначает техников и управляет оперативной работой;
- руководитель видит KPI команды, стоимость, финально закрывает/возобновляет заявки и видит журнал контроля;
- администратор имеет полный доступ к пользователям, ролям, настройкам, интеграциям и API;
- вложения защищены авторизацией и областью доступа к заявке;
- Swagger/OpenAPI доступен только администратору;
- критичные действия, входы и отказы в доступе пишутся в `Журнал контроля`;
- завершение внутренней заявки требует исполнителя, комментария мастера и минимум 1 минуту зафиксированного времени.

## Главное изменение v0.3

Источником данных является **сама база ТОиР**. Раздел `Настройки` позволяет администратору
менять названия, цвета и порядок статусов, приоритетов и статусов оборудования, SLA приоритетов,

## Быстрый запуск на Windows — чистая система

1. Распакуйте архив.
2. Запустите `run_windows.bat`.
3. Откройте `http://127.0.0.1:8000`.
4. Вход по умолчанию: `admin` / `ChangeMe123!`.
5. Сразу измените пароль в `Профиль`.

При первом запуске создаются только администратор и системные справочные значения. Объекты,
оборудование и пользователи добавляются через интерфейс.

> Для локального HTTP в `.env` должно быть `COOKIE_HTTPS_ONLY=false`.
> После публикации через HTTPS установите `COOKIE_HTTPS_ONLY=true` и правильный `PUBLIC_BASE_URL`.

## Демо-режим

Для презентации с готовыми примерами запустите:

```text
run_demo_windows.bat
```

Он создаст тестовые объекты, оборудование, ППР, ЗИП, подрядчика и пример заявки.
Демо-данные добавляются только если соответствующие таблицы пусты.

## Docker + PostgreSQL

Для рабочего сервера:

1. Скопируйте `.env.example` в `.env`.
2. Измените `SECRET_KEY`, `INITIAL_ADMIN_PASSWORD`, `POSTGRES_PASSWORD`.
3. При внешнем HTTPS укажите `PUBLIC_BASE_URL` и `COOKIE_HTTPS_ONLY=true`.
4. Запустите:

```bash
docker compose up -d --build
```

Контейнеры:

- `toir` — FastAPI/PWA;
- `db` — PostgreSQL 16.

PostgreSQL хранится в Docker volume `toir_pgdata`, загруженные файлы — в каталоге `uploads`.

## Интеграция с 1С — опционально

По умолчанию:

```env
ONEC_ENABLED=false
ONEC_AUTO_PUSH=false
```

В этом режиме приложение не обращается к 1С, а входящие webhook 1С отключены.

Если клиенту нужна 1С, установите `ONEC_ENABLED=true` и заполните `ONEC_*` в `.env`.
`ONEC_AUTO_PUSH=true` включает автоматическую отправку изменений заявок; при `false` обмен
можно запускать вручную из раздела `Интеграции`.

Подготовленный ранее коннектор находится в:

```text
integrations/1c/
```

Он оставлен для совместимости с документом `ЗаявкаХозОтдела` и ранее подготовленными HTTP-сервисами.

## Переход с v0.2.2

Если уже есть `toir.db` от v0.2.2:

1. остановите старую версию;
2. сделайте копию `toir.db` и папки `uploads`;
3. положите БД рядом с v0.3;
4. запустите `run_windows.bat`.

Существующие заявки и оборудование сохраняются. Последние значения подсветок, ранее полученные
из 1С, становятся обычными локальными настройками системы и дальше редактируются в ТОиР.
Поля `one_c_id` сохранены исключительно для будущего коннектора.

## Безопасность перед показом/боем

- измените пароль администратора;
- задайте длинный случайный `SECRET_KEY`;
- при Docker измените `POSTGRES_PASSWORD`;
- для внешнего доступа используйте HTTPS;
- не открывайте PostgreSQL и порт 8000 напрямую в Интернет;
- включите `COOKIE_HTTPS_ONLY=true` после настройки HTTPS;
- включайте коннекторы только если они реально используются.

### QR-коды и публичный адрес

FMTS v0.4.1 больше не зашивает `127.0.0.1:8000` в QR-коды. Для Render задайте переменную окружения:

```env
PUBLIC_BASE_URL=https://fmts-demo.onrender.com
```

Если `PUBLIC_BASE_URL` не задан, FMTS сначала попробует `RENDER_EXTERNAL_URL`, затем старый `BASE_URL`, а после этого определит адрес из текущего HTTP-запроса. Для стабильных напечатанных QR-кодов в production рекомендуется всегда задавать `PUBLIC_BASE_URL`.


## KPI ремонтников — v0.5.0

Раздел **KPI / Рейтинг** формирует месячный отчёт по пользователям с ролью `Техник`.
Руководитель, диспетчер и администратор видят рейтинг всей команды, а техник — только собственные показатели.
Отчёт можно выгрузить в CSV для Excel или распечатать / сохранить в PDF.

Базовая формула: SLA 40% + закрытие 25% + производительность 20% + документирование 15%.
Цель по производительности по умолчанию — 30 взвешенных баллов в месяц и меняется через `KPI_MONTHLY_TARGET_POINTS`.


## Учёт времени по заявкам — v0.5.1

В карточке заявки ремонтник может нажать **«Начать работу»**, а после завершения этапа — **«Остановить таймер»**. FMTS сохраняет каждый сеанс работы с сотрудником, временем начала/окончания, длительностью и комментарием.

Один сотрудник не может одновременно учитывать время по двум заявкам: запуск нового таймера автоматически завершает предыдущий. При закрытии/отмене заявки или смене исполнителя активный таймер также останавливается.

Если таймер забыли включить, время можно добавить вручную. Общая длительность видна в карточке и списке заявок, а месячный KPI-отчёт показывает фактически учтённые часы по каждому ремонтнику. Эти часы информационные и пока не меняют итоговый процент KPI.

## Материалы и стоимость заявки (v0.5.4)

В карточке заявки FMTS хранит историю фактически списанных материалов. Новое списание сохраняет количество и цену на момент операции, поэтому изменение цены в складском справочнике не переписывает историю. Стоимость материалов автоматически включается в `parts_cost`, а для руководителя/администратора выводится итог: работы/услуги + материалы.

## FMTS v0.6.0 — Enterprise ServiceDesk Pack

В системе появился дополнительный ServiceDesk-контур поверх существующих функций ТОиР: каталог сервисов, собственные поля форм, автоматическая маршрутизация и эскалация SLA, база знаний, связанные заявки, согласования, глобальный поиск, сохранённые фильтры, конструктор отчётов и подписки на отчёты.

Центр уведомлений поддерживает внутренние события, а при наличии настроек — SMTP, Telegram, WhatsApp webhook и Web Push для PWA. Входящие письма через IMAP могут создавать новые заявки; если тема содержит существующий номер вида `SR-YYMMDD-NNN`, письмо добавляется как комментарий к заявке.

CMDB расширена родительскими/дочерними узлами, владельцем и критичностью оборудования. Автоназначение может учитывать текущую загрузку и график доступности техников.

Безопасность: пользователи могут включить TOTP 2FA; дополнительно можно подключить LDAP / Active Directory. Локальные учётные записи продолжают работать независимо от LDAP.

Все новые внешние каналы **выключены по умолчанию** и не требуются для запуска FMTS. Параметры находятся в `.env.example`.

## v0.7.3 — CMDB / Categories / Labor Analytics

Версия 0.7.3 расширяет FMTS блоком CMDB и аналитики трудозатрат. В разделе **ТОиР и активы → Импорт данных** можно массово загрузить оборудование/CMDB и складские позиции из `.xlsx` или `.csv`; из интерфейса доступны готовые Excel-шаблоны. Импорт оборудования умеет создавать отсутствующие объекты, обновлять записи по инвентарному номеру, связывать родительское оборудование и владельца.

В разделе **Service Desk → Классификаторы** появились иерархические категории для заявок, оборудования, базы знаний и сервисов. В формах отображается полный путь категории, поэтому можно строить структуру вроде `Холодильное оборудование → Морозильные бонеты → Плановое ТО`.

Глобальный поиск получил упрощённую морфологию русских слов и ранжирование результатов: разные словоформы вроде «холодильник / холодильника / холодильники» находятся без обязательного точного совпадения.

Для сотрудников можно задать расчётную ставку в тенге за час. При завершении рабочего сеанса FMTS сохраняет **снимок ставки** и стоимость этого сеанса, поэтому последующее изменение ставки не переписывает исторические затраты. Итоговая стоимость работ в заявке состоит из стоимости фактического времени плюс отдельной ручной суммы дополнительных работ/услуг.

Новый раздел **Аналитика → Трудозатраты** показывает сотрудников, заявки, объекты, продолжительность, ставку и стоимость работ, поддерживает фильтры и CSV-выгрузку. Для старых сеансов доступен безопасный пересчёт только тех записей, у которых стоимость ещё не была сохранена.

## v0.7.5 — Advanced ITSM / SLA / CMDB / Webhooks

Версия 0.7.5 добавляет следующий enterprise-блок. Заявки разделяются на инциденты, запросы, проблемы и изменения. Для изменений можно задавать плановое окно работ, а отдельный экран `ITSM / Изменения` показывает открытые проблемы, календарь изменений и нарушения SLA.

SLA теперь умеет считать рабочее время по календарю: дни недели, часы работы, часовой пояс и праздничные даты. У сервиса отдельно задаются норматив первой реакции и норматив решения. Первая реакция фиксируется автоматически при рабочем действии сотрудника.

CMDB получила произвольные зависимости между единицами оборудования — питание, резервирование, сеть и другие связи — поверх уже существующей родительской иерархии.

Интеграционный контур расширен исходящими webhooks с очередью, повторными попытками и HMAC-SHA256 подписью для n8n и внешних систем.


## v0.7.6 — Mobile UX / Interactive ТО / Knowledge Files

Версия основана на v0.7.5 и сфокусирована на ежедневной работе ремонтников. База знаний теперь поддерживает вложения DOCX, PDF и изображения. Файлы хранятся защищённо, изображения и PDF можно открыть в браузере, документы — скачать. Добавлять файлы можно сразу при создании статьи и позже из карточки статьи.

## v0.7.6.1 — упрощённый конструктор чек-листов

## v0.7.6.2 — плановое ТО, SLA и уведомления

ППР/ТО теперь создаёт системную заявку заранее. Создатель — **Система**, заявитель — **объект оборудования**, тип обращения — **Плановое ТО**. SLA выполнения привязан к плановой дате обслуживания, а новый цикл плана начинается только после фактического выполнения текущей ППР-заявки.
